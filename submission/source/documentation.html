01 · Overview

Problem statement and objectives

In most of my own courses, the reading material sat in a Drive folder, deadlines were announced in a WhatsApp group and marks came back in a spreadsheet. It was easy to miss something that was due, and the instructor had no simple way to see who had fallen behind.

LearnSphere puts all of this in one website. Students, instructors and admins each get their own pages, and everything (courses, submissions, marks and progress) is stored in one database behind one REST API.

Objectives

  • Secure registration and login, with role-based access for students, instructors and admins.
  • Instructors can create, edit and delete courses, organise them into ordered modules and publish assignments.
  • Students can browse the catalog, enroll, study module material and submit assignments.
  • Progress is calculated from completed modules and shown as percentages, progress bars and status.
  • Instructors review submissions, award marks, write feedback or request a resubmission.
  • Build and deploy every layer myself: frontend, API, login, database and hosting.

02 · Users

User roles and access control

Hiding a button in the interface is not enough, so every one of these rules is also checked by the server.

RoleCapabilitiesMain screens
StudentRegister and log in, browse and filter courses, enroll or leave, study modules, pass module quizzes, submit text, links or files until graded, view marks and feedback, ask questions in the course discussion, keep personal notes, track progress and earn certificates.Dashboard, Catalog, My Courses, Module view, Assignments, Profile
InstructorCreate, edit, publish and delete their own courses; add, reorder and delete modules with learning materials; create assignments with deadlines and maximum marks; review submissions; give marks and feedback or request a resubmission; view the roster with each student's progress; build module quizzes; export the gradebook as CSV; send announcements; answer course discussions.Dashboard, Manage Courses, Course Editor, Submissions
AdminEverything an instructor can do, on every course. Also: view all users, change roles, activate or deactivate accounts, transfer course ownership, send platform announcements and see platform statistics.Dashboard, Users, all instructor screens

How a request is authorised

  1. The user signs in with Firebase (email/password or Google). Firebase stores the password as a salted hash and returns a short-lived signed ID token (a JWT).
  2. The React client sends that token with every API call in the Authorization: Bearer header.
  3. The authenticate middleware verifies the token with the Firebase Admin SDK, then loads the matching row from the users table, creating it on first login. Deactivated accounts are rejected with 403.
  4. requireRole() checks the role for the route, and ownership helpers (assertCanManage, isEnrolled) check that the user owns the course or is enrolled in it.
The browser never talks to the database. Row Level Security is switched on for every table and no public policies exist, so the public Supabase key cannot read anything. Only the server, which holds the service role key, can query the data.

Onboarding

On first login a new user chooses I want to learn or I want to teach. Emails listed in the server's ADMIN_EMAILS setting are made admins automatically. Admins can change any user's role later.

Design decisions

  • I used Firebase for logins because it already handles password hashing, Google sign-in and reset emails, and Supabase for the data because the course data is relational and fits PostgreSQL well.
  • Progress is not saved as a number. It is worked out from lesson_progress each time (finished modules divided by total modules), so it stays right when an instructor adds or removes a module.
  • Each route copies only the fields it expects from the request body before writing anything, so extra fields sent by a client are ignored.
  • Helmet adds the standard security headers, CORS only accepts requests from my own frontend, and there is a rate limit on the API.

Interface

I wanted the site to look like a printed course book rather than a typical admin dashboard, so it uses a cream background, dark brown text, a single terracotta accent and serif headings, with the word विद्या (knowledge) as a faint watermark. On phones the top menu turns into a full-screen menu, and the layout works down to about 360 px wide.

Setup, deployment and demo accounts

Local setup

git clone https://github.com/abhyudaysaksena06/QuillanceMaajorProject_1.git
cd QuillanceMaajorProject_1
npm run setup

# 2. database: run database/setup_all.sql in the Supabase SQL Editor
# 3. fill in server/.env and client/.env (see the .env.example files)

# 4. demo accounts and sample progress
npm run seed:demo

# 5. start API (port 5000) and web app (port 5173) together
npm run dev

Production deployment

  • Frontend on Vercel (root client, Vite preset). vercel.json rewrites every path to index.html so client-side routes survive a refresh.
  • Backend on Render (root server, npm start). Secrets are stored as Render environment variables.
  • Database on Supabase; authentication on Firebase, with the Vercel domain added to Authorized domains.

07 · Closing

Outcome and future work

LearnSphere is live and covers everything the brief asked for, plus most of the optional features. Instructors and admins manage courses, modules, quizzes and assignments, and students enroll, finish modules, hand in work and get marks, feedback and certificates. Building it meant getting a React frontend, an Express API, Firebase logins, a PostgreSQL database and two hosting services to work together.

Challenges

  • Login lives in Firebase but the data lives in Supabase. The server checks the Firebase token on every request and links each Firebase user to a row in my users table.
  • A hosted database is reachable from the internet, so I turned on Row Level Security and kept the service key on the server only.
  • A stored progress percentage went wrong whenever a module was added, so progress is now calculated from the finished modules instead.
  • After deploying, the browser blocked calls from Vercel to Render. A CORS allow-list read from an environment variable fixed it.
  • The quiz answers must not reach the browser, so the server removes them before sending a module to a student and marks the answers itself.

Future improvements

  • Course ratings and reviews
  • Live classes and attendance tracking
  • Real-time notifications over WebSockets instead of polling
  • Automated tests that run on every push
